3. SECURITY ARCHITECTURE (ZERO-COMPROMISE MODEL)
----------------------------------------------------------------------

Layer 1 — Transport & API:
  - All traffic encrypted via HTTPS (Vercel + Supabase)
  - API keys stored in .env.local (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)
  - Service role key NEVER exposed on frontend

Layer 2 — Authentication (Supabase Auth / JWT):
  - Short-lived JWTs auto-refreshed by Supabase JS client
  - Bcrypt-hashed passwords managed securely by Supabase Auth
  - Role management via `role` column in profiles table
  - Protected routes check user + role client-side
  - Admin escalation prevented server-side via RLS policies

Layer 3 — Database (Row Level Security):
  - profiles: Owner select/update only (no role self-escalation)
  - products: Public select; Admins only for insert/update/delete
  - orders: Owner + Admins select; Owner insert only; Admins update status; No delete

Layer 4 — Business Logic (Atomic RPC):
  - Stock deduction in PostgreSQL transaction using `SELECT ... FOR UPDATE`
  - Prevents race conditions during concurrent checkouts

Layer 5 — Frontend Validation:
  - TypeScript strict mode
  - Form validation before API calls
  - Out-of-stock items disabled in UI
  - Admin routes guarded by <ProtectedRoute requireAdmin />

4. DATA FLOW DIAGRAMS
----------------------------------------------------------------------

[Auth Flow]
  User fills Sign Up Form (name, email, password)
    -> supabase.auth.signUp(...)
    -> Creates auth.users record
    -> Database trigger `handle_new_user()` creates public.profiles row
    -> JWT returned to client -> stored by Supabase SDK
    -> AuthContext updates state -> User redirected to home

[Checkout Flow — Race Condition Safe]
  User clicks "Place Order"
    -> Client calls supabase.rpc('place_order_atomic', { p_user_id, p_items, p_total_amount })
    -> PostgreSQL begins TRANSACTION
    -> Auth check: validates auth.uid() == p_user_id
    -> FOR EACH item:
         SELECT stock, name FROM products WHERE id = ? FOR UPDATE  (ROW LOCKED)
         IF stock < quantity -> RAISE EXCEPTION 'OUT_OF_STOCK' (TX ROLLBACK)
         UPDATE products SET stock = stock - quantity
    -> INSERT INTO orders (user_id, products, total_amount, order_status)
    -> COMMIT -> Lock released
    -> Client receives { success: true, order_id }
    -> Cart cleared -> Navigate to /profile

[Concurrent Checkout Scenario]
  TX1: acquires lock on product row -> stock=1 -> deducts -> stock=0 -> COMMIT
  TX2: waits for lock -> lock released -> re-reads stock=0 -> RAISES EXCEPTION
  TX2 client: receives "OUT_OF_STOCK" error toast -> double-purchase prevented!
